# tetris-gc

C++20 / OpenMP Tetris genetic optimization and endurance experiments. The executable
is `tetris-gc`; the workspace directory is currently named `tetris-mc`.

## Build

```sh
cmake -S . -B build -DCMAKE_BUILD_TYPE=Release -DTETRIS_NATIVE=ON
cmake --build build -j
ctest --test-dir build --output-on-failure
```

Requires CMake 3.20+, C++20 and OpenMP. No runtime downloads or Python packages.
Leave `TETRIS_NATIVE` off for binaries distributed to other CPUs. Python and Node
are optional test dependencies: when available, CTest also checks binary experiments
and compares the C++ implementation directly with the original JavaScript fixtures.

## Experiments

All persistent output uses versioned **little-endian binary `.tgc` files**. Default
console output is one completion/pause line; `--verbose` enables generation progress.
Text/JSON/CSV output is no longer generated by training or evaluation.

Article-sized training, replicated over five independent optimizer seeds:

```sh
./build/tetris-gc train --population 1000 --games 100 --pieces 500 \
  --generations 100 --runs 5 --threads 8 --sampling independent \
  --output results/training.tgc
```

The generation count is an experiment choice: the article did not specify a count.
Generation 0 evaluates the initial population; subsequent generations replace 30%.
The checkpoint stores every run's complete population, RNG state, candidate IDs,
convergence history and per-game validation states. Each run uses `seed + run_index`.
The default validation compares its winner and the published baseline over 100 fresh
paired games with a 500-piece cap. Increase `--validation-pieces` to test durability:

```sh
./build/tetris-gc train --population 100 --games 10 --generations 10 --runs 3 \
  --validation-games 100 --validation-pieces 100000 --threads 8
```

Training game sampling is selectable:

- `common` (default): fixed common sequences across all candidates and generations;
  cached survivor fitness, deterministic comparisons with little sampling noise.
- `independent`: independent sequences per candidate, matching the original tuner's
  sampling approach; cached survivor fitness. Seeds are derived deterministically.
- `refresh`: new common sequences each generation; survivors are re-evaluated so
  their fitness remains comparable with the new offspring.

Resume, optionally increasing the target generation:

```sh
./build/tetris-gc train --resume results/training.tgc --generations 200 --threads 8
```

Configuration is restored from the checkpoint. Resume accepts `--threads`, `--output`,
`--verbose`, `--checkpoint-pieces` and an increased generation target (training) or
piece cap (endurance). Other overrides are rejected. Extending training discards its
old validation states and validates the new winner after additional generations.

Evaluate all trained winners against one published baseline on **identical game seeds**:

```sh
./build/tetris-gc endurance --weights-file results/training.tgc \
  --games 100 --pieces 10000000 --threads 8 --seed 42 \
  --checkpoint-pieces 100000 --output results/endurance.tgc
```

Ten million pieces can clear at most four million lines on a ten-column board, so
this cap is large enough to attempt a run comparable with the article's multi-million
line demonstration. It does not guarantee survival. Games stop at topout or the piece
cap; reaching the cap is recorded as **right-censored**, rather than a loss.

`--weights-file` automatically adopts the training rules and includes every available
run's evaluated winner. An explicitly conflicting `--rules` is rejected. The last
policy is the published baseline unless `--no-baseline` was supplied. Without custom
weights, only the baseline is evaluated. Explicit costs are also supported:

```sh
./build/tetris-gc evaluate --weights 0.510066,0.35663,0.184483,-0.760666 \
  --games 1000 --pieces 10000 --threads 8 --output results/evaluation.tgc
./build/tetris-gc evaluate --rules battleblocks --weights 510,869,184,-761
```

Weight order is **height, holes, bumpiness, lines**; lower costs win. Weights are
normalized without intentionally changing their ranking. `evaluate` and `endurance`
use the same resumable engine; their default caps differ (500 versus 10,000,000).
The independently seeded validation/test sets never affect genetic selection.

Press **Ctrl+C** to save and stop. Training preserves the last completed generation;
partial generation evaluations are discarded and replayed on resume. Endurance saves
live boards, bag permutations, RNG states, both upcoming pieces and counters, so games
continue from the interrupted position. Interrupt handling checks between games and
every 1,024 moves inside a game. Exit code 130 indicates a paused run.

```sh
./build/tetris-gc endurance --resume results/endurance.tgc --threads 8
# Also continue games that previously reached a smaller administrative cap:
./build/tetris-gc endurance --resume results/endurance.tgc --pieces 20000000
```

Piece bags are generated incrementally. Memory use depends on populations and game
counts, **not the piece cap**. OpenMP parallelizes candidate × game training jobs and
independent endurance games. Each job owns its board and RNG; no per-move locks are
needed. `--threads 0` respects runtime defaults, including `OMP_NUM_THREADS`.
A single endurance game runs on one thread because its moves are sequential.

## Statistics

```sh
./build/tetris-gc report --input results/endurance.tgc --output results/statistics.tgc
./build/tetris-gc report --input results/training.tgc --output results/validation.tgc
python3 tools/read_tgc.py results/training.tgc
python3 tools/read_tgc.py results/statistics.tgc
```

`report` preserves raw per-game records and adds binary summaries per policy:

- Mean, median, 5th/95th percentiles of observed lines and pieces.
- Sample standard deviation of lines and an approximate 95% normal interval for
  the mean. `mean_ci_available` is false for one-game or unfinished batches.
- Separate counts of topouts, administrative caps and still-active games.
- Kaplan-Meier survival estimates at 1,000, 10,000, 100,000, 1,000,000 pieces and
  the configured cap. `identifiable=false` marks horizons beyond observed support.
- Wilson 95% intervals when survival at a horizon is fully observed; log-log
  Greenwood intervals with earlier censoring. Degenerate Greenwood endpoints with
  early censoring use conservative [0,1] bounds instead of implying certainty.

These means/percentiles describe **observed outcomes at the experiment's cap**; they
are not estimates of uncensored lifetime when games remain alive. Incomplete batches
are progress snapshots; their unequal exposure makes direct mean comparisons premature.
Survival curves account for censored games. Pairing makes per-game differences between
winners and baseline available for further analysis through the included Python reader.

The reader uses only the Python standard library and exposes `read(path)` for analysis.
Its default output is brief. `--json` explicitly decodes all records to stdout when
inspection or interoperability needs text. See [BINARY_FORMAT.md](BINARY_FORMAT.md)
for the schema. Files have payload-length and checksum validation; snapshots are
written to a temporary file and atomically renamed under WSL/Linux. This protects
against interrupted writes, without promising durability after power loss.

## Reproduction and validation

The `article` default now follows the retrieved [original browser implementation](https://github.com/LeeYiyuan/tetrisai):
central square-matrix spawning, clockwise rotations, the actual source's horizontal/
upward kick search, reachable spawn-row horizontal placements, and its tie order.
Hypothetical lookahead placements are scored before clearing lines; real placements
clear lines before checking the two hidden rows for topout. The source's null-score
behavior when the next piece cannot spawn is preserved. If the current piece has no
valid placement, the simulator records a topout instead of reproducing a JavaScript
null dereference.

The browser source's kick routine is simpler than standard SRS, despite the article's
SRS description. We match the source, and include MIT-licensed reference fixtures
for regression checks. This cannot recover the unpublished seeds or guarantee the
same numerical weights or endurance record as the historical experiment.

`article-drop` retains the earlier unrestricted normalized hard-drop approximation
for comparisons. `battleblocks` uses a 20-row board, no lookahead and its nonlinear
bumpiness table with baseline costs `510,869,184,-761`. Neither mode adds interactive
gravity timing, hold, multiplayer garbage, or controller stalls.

Tests cover cell-grid placement/scoring, original JavaScript placement parity,
streaming versus precomputed bags, cell conservation, deterministic parallel runs,
training resume for all sampling modes, endurance continuation, paired seeds,
statistical calculations, binary checksums, and graceful interruption.

```sh
cmake -S . -B build-sanitize -DCMAKE_BUILD_TYPE=Debug -DTETRIS_SANITIZE=ON
cmake --build build-sanitize -j
ctest --test-dir build-sanitize --output-on-failure
./build/tetris-gc benchmark --games 1000 --pieces 500 --threads 1
./build/tetris-gc benchmark --games 1000 --pieces 500 --threads 8
```

`benchmark` runs the evaluation kernel without file writes. Its time includes game
initialization and incremental bag generation. Compare identical rules, seeds and
caps across thread counts; throughput counts actual moves, including early losses.
